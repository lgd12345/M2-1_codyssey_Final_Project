# 현재 화면 기준 개발 범위

현재 화면의 구성과 사용자 업무가 범위의 기준이다. 기존 백엔드에 기능이 있다는 이유로 관리 화면·가입 등의 범위를 늘리지 않는다.

## 현재 구현 상태

| 화면·기능 | 현재 상태 |
|---|---|
| 공개 홈·고객센터·로그인 | 유지, 실제 인증·세션·로그아웃 |
| 고객 요청 접수·목록·상세 | 실제 API/DB 연결, 회사 단위 공유·다른 회사 접근 차단 |
| 운영진 대기열·요청 상세 | 실제 API/DB 연결 |
| AI 분석·원인·부품·부서별 초안 | 운영진이 `AI 분석 시작`으로 실행, 실제 매뉴얼·과거 사례 검색 기반 결과를 저장·표시(`013_service_analysis`). 분석만으로 승인·부서 업무는 생기지 않음 |
| 승인·반려·재분석·담당자 지정·메모·고객 답변 | 실제 API/DB 연결(`014_service_workflow`). 서버가 행위자·시각·업무 번호를 결정하고 상태 전이를 잠금으로 직렬화 |
| 부서 업무·처리 결과 | 승인된 초안으로 생성된 실제 업무를 시작·완료하고, 모든 업무 완료 후에만 종결 |
| 고객 정보 추가·콜백·종결 요청 | 실제 API/DB 연결. 정보 요청 상태에서 고객 답변은 재분석을 시작 |
| 첨부·PDF 열람·AI 평가 저장 | 미연결 표시(가짜 업로드·저장·평가 성공 없음). 부서 선택은 운영진 보기 필터이며 부서 소속 권한은 아직 모델링하지 않음 |
| 분석 공통 기반 | 기존 매뉴얼·FSR 검색, 원본 열람·인용 검증, 비스트리밍 실행 API 유지 |

요청 상태는 실제 접수 시 `접수됨`이다. 분석 작업을 실행하지 않았는데 `분석 중`으로 표시하거나 자동 완료하지 않는다.

## 제거한 시연 장치

- 샘플 요청·분석·부서 업무·고객사·장비·보증 데이터
- 입력 키워드에 따른 고정 시나리오 선택
- 750ms 타이머와 가짜 분석 단계 진행
- 답변 글자 수에 따른 고정 분석 성공 결과
- 브라우저의 번호·시각·처리자 결정과 프런트 전용 업무 상태 변경
- `?company=`로 고객사를 바꾸는 개발용 우회
- 전송하지 않는 파일을 선택만 하게 하거나 AI 평가를 저장한 것처럼 보이는 동작

업무 규칙은 `frontend/src/domain/workflow.js`와 테스트에 남겼다. 실제 상태 전이·권한 검사는 후속 서버 구현에서 검증한다. 부서 선택 필터는 운영진 보기 필터일 뿐 사용자 소속 권한을 결정하지 않는다.

## 첫 실제 업무 단위

`backend/app/service_requests/`와 `012_service_requests.sql`은 최소 접수 기능만 제공한다.

- 서버 세션에서 실제 사용자 확인, 쓰기는 CSRF/Origin 검사
- 고객사 소속으로 등록 장비·회사 요청 범위 제한
- 장비 선택 후 서버가 회사·기계 정보를 조회해 접수 시점 스냅샷 저장
- 서버에서 번호·시각·작성 계정을 결정하고 트랜잭션으로 저장
- 같은 회사 동료·운영진 조회, 다른 회사 요청 상세는 404
- 고객 응답에는 분석·초안·승인 등 운영진 전용 필드를 포함하지 않음
- 소속 미등록은 기본 고객사로 대체하지 않고 명시적으로 안내
- 스키마 미적용은 503, 자동 마이그레이션·샘플 생성 없음

초기 TDD는 격리 DB에서 수행했다. 이후 사용자 승인으로 현재 로컬 앱의 `service_poc_test`에 **012만 적용**했다. 기존 활성 고객사 1개를 같은 ID·이름으로 재사용해 `user`를 연결했으며, 기존 명부에는 장비가 없어 명시적인 **E2E 검증용 장비** 1건을 준비했다. 이 장비는 실제 장비 정보가 아니다. 실제 장비 명부의 일괄 이관·관리 기능을 추가한 것은 아니다.

`admin`/`user` 실제 계정과 현재 DB를 사용하는 로컬 Playwright 인수 검증을 통과했다. 테스트가 만든 요청과 임시 타사 고객사·장비는 정리하고, 적용한 스키마와 `user`의 소속·검증용 장비는 유지했다. 기존 코퍼스·계정 비밀번호·역할·이전 고객사 명부는 변경하지 않았다. 기존 데이터가 자동으로 새 테이블에 연결되는 것은 아니다.

## 계속 제외하는 기능

고객사·연락처·장비 관리 CRUD, 회원가입·이메일 인증·비회원 문의·SMTP, 웹 DB 설치·진단, 옛 문서 현황·독립 채팅·AI SDK 스트리밍 기능은 복원하지 않는다. 관련 과거 파일은 별도 archive 없이 제거했다.

`rag_case`는 검색용 과거 FSR 자료이지 현재 요청 저장소가 아니다. 운영진은 `admin`, 발급 고객은 `user`이며 기존 `customer` 로그인 호환성은 유지한다. 이메일 로그인 정규화를 위한 `email-validator`는 인증 의존성이므로 유지한다.

검증 방법과 DB 안전 경계는 [TDD 지침](tdd.md)을 따른다.
