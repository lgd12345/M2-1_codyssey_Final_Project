# PRD: 매뉴얼 검색·원본 확인 에이전트 (백엔드)

상태: 핵심 백엔드 에이전트/검색/원본 열람 경로 구현. 실제 Gemini 단건 임베딩 및 LLM의 식별자 조회→PDF 이미지 열람→인용 스모크 통과. 전체 코퍼스 임베딩 색인·골든셋 품질평가·성능 검증·검색 경로 병렬화는 남아 있다. UI/UX와 사용자 응대 정책은 범위 밖이다.

## 1. 목적과 사용자

상위 백엔드가 요청을 전달하면 LLM 에이전트가 도구를 선택해 공작기계 매뉴얼을 검색하고, 필요한 경우 원본 PDF 페이지를 직접 확인한다. 결과는 답변, 출처, 이번 실행에서 확인한 원본 이미지 참조, 도구 실행 상태를 구조화해 반환한다. 에이전트의 도구 판단은 모델이 수행한다.

## 2. 범위

### 포함
- 전처리 산출물 및 원본 PDF의 멱등 적재
- PostgreSQL 기반 정확 식별자·키워드·벡터 검색 및 RRF 결합
- PDF 원본 페이지를 에이전트가 요청할 때 렌더링하고 이미지와 텍스트를 제공하는 도구
- OpenAI 호환 프록시를 쓰는 도구 호출 에이전트와 CLI 실행기
- 도구 계약, 검색 품질 및 장애 경로의 TDD 테스트
- 테스트 데이터는 로컬에서만 보관하고 git에서 제외

### 제외
- 프론트엔드, 사용자용 문구와 UI/UX
- 임베딩 장애 후 사용자에게 어떻게 말하고 멈출지에 대한 제품 정책
- 로그인/대화 영속성/서비스데스크 티켓·메일 등 추가 도구
- 썸네일, 사전 전체 페이지 렌더링, 이미지 임베딩, reranker, 분산 검색
- 에이전트 호출 수/시간/토큰 예산 제한

## 3. 조사로 확정한 환경 사실

- DB: PostgreSQL 17.11, pgvector 0.8.7. `pg_trgm`은 설치 가능하며 현재 DB에는 아직 설치되지 않았다. 테스트 DB는 개발 DB와 별도로 둔다.
- 코퍼스 샘플: md/pdf 원본 각 67개 엔트리 중 36개 고유 SHA-256. 모든 md 결과 JSON의 `source_sha256`이 대응 PDF SHA-256과 일치한다. 샘플에 변환 페이지 레코드 3,333개가 있고, 더 많은 자료가 추후 추가될 예정이다.
- 변환 텍스트는 순수 OCR이 아니다. PDF 텍스트 레이어 추출과 OCR/검증 파이프라인을 거쳤고, 184페이지는 LLM 경로를 이용했다. 현재 집계는 `verified` 1,896, `corrected` 852, `needs_review` 585 페이지다. 그러므로 에이전트에는 **OCR/텍스트 추출 등 자동 변환 결과**라고 명시하고, 페이지에 따라 OCR이 아닌 PDF 내장 텍스트 추출 결과일 수도 있음을 알린다.
- 페이지 분류는 표, 본문, 분해도, 도식, 래스터 그림, 목차, 표지 등을 포함한다. 분류는 **레이아웃 기준이라 내용을 보장하지 않는다**: 분해도로 분류된 177쪽 중 61쪽은 실제 절차·표·부품 조립품 명칭이 있는 본문이었다. 따라서 분해도는 분류가 아니라 **읽을 수 있는 본문(이미지 표기를 뺀 200자 이상, 단어 15개 이상)이 있을 때만** 색인하고, 호출선 번호·OCR 조각뿐인 페이지는 제외한다(도면 자체는 연결된 표 페이지에서 `open_source`로 열람). 목차는 제목이 실제 본문보다 높게 노출되므로, 표지는 원문 텍스트가 없으므로 색인하지 않는다.
- Gemini OpenAI 호환 프록시의 `gemini-embedding-2`는 현재 설정에서 3072차원을 반환했고 `dimensions` 인자를 무시했다. 한 요청 배치는 최대 100개였다. 측정 중 429를 경험했으며 일시 후 회복했다. 이 수치는 라이브 테스트 관측치이지 제공자의 영구 보장으로 취급하지 않는다.
- pgvector 0.8.7에서 `vector(3072)` HNSW 인덱스는 생성할 수 없었다. 정확 검색은 10,000행 합성 데이터에서 약 608ms였고, `halfvec(3072)` HNSW는 약 37ms였으나 인덱스 생성에 약 182초가 들었다. 초기 샘플은 exact search로 시작하고 실측 기준을 넘으면 별도 평가 후 최적화한다.
- PostgreSQL의 `simple` FTS는 한국어 조사/부분 용어를 놓쳤다. 한국어 2-gram과 영문·숫자 토큰을 만든 테스트에서는 샘플 쿼리 재현율이 `ILIKE`와 같고, 33,000페이지 합성 반복에서 4–32ms였다. 이 방식은 한국어 형태소 분석기가 아니므로 실제 골든셋으로 계속 검증한다.
- PDF 페이지 렌더링은 pypdfium2로 온디맨드 수행한다. 샘플 측정에서 150dpi 기준 약 0.3–0.4초, PNG 약 67–249KB였다. 이미지 파일은 검색/적재 시 미리 만들지 않는다.
- 정처기 프로젝트의 실측에서는 OpenAI 호환 Chat Completions가 이미지 입력과 네이티브 도구 왕복을 지원했다. 이 프로젝트에서도 같은 프록시 패턴을 쓰되 실제 모델 설정은 `backend/.env`에 둔다.

## 4. 제품 요구사항 및 불변 조건

1. **원본 우선 / 변환 출처 명시.** PDF가 원본 근거다. 검색 결과는 `text_origin=ocr_or_text_extraction`와 검증 상태(`verified|corrected|needs_review`)를 포함한다. 시스템 프롬프트는 이 변환 결과가 틀릴 수 있음을 밝히고, 코드·수치·부품번호처럼 정확도가 중요한 주장 또는 `needs_review` 결과는 `open_source`로 원본을 확인하도록 지시한다.
2. **정확 식별자 검색.** 부품번호, PMC 주소, 문서에서 식별되는 알람 번호를 종류별 정규화 후 정확 일치로 찾는다. 오타/유사 문자열은 exact 결과로 간주하지 않는다. 종류를 확인하지 못하는 숫자는 무분별하게 알람 번호로 만들지 않는다.
3. **하이브리드 검색.** 정확 식별자 조회를 검색 결과에 우선 결합하고, 키워드(한글 2-gram tsvector + typo 보완)와 Gemini 벡터 검색을 병렬 수행한다. 점수 스케일을 직접 더하지 않고 RRF로 결합한다. 각 검색 경로의 상태를 반환한다.
4. **임베딩 장애 상태 전달.** 질의 임베딩은 재시도한다. 그래도 실패하면 도구 결과에 vector 상태와 안전한 오류 분류를 반환한다. 이 단계에서는 사용자용 응답 문구/자동 중단 정책을 확정하지 않는다.
5. **중복/증분 적재.** 원본 PDF SHA-256은 문서의 식별자다. 동일 PDF는 하나만 저장하고 원래 경로들을 별칭으로 보존한다. 내용이 같은 페이지는 embedding hash를 공유할 수 있지만 별도 기종/문서 출처 관계는 보존한다. 반복 적재는 멱등이고 원문이나 hash가 바뀌면 새 버전으로 기록한다.
6. **임베딩 재사용과 설정 격리.** 문서 임베딩은 DB에 저장한다. 같은 텍스트 해시와 같은 임베딩 설정이면 재호출하지 않는다. 모델/차원/입력 포맷이 다른 벡터를 함께 검색하지 않는다. Gemini 배치는 100개 이하이며 색인은 중단 후 재개할 수 있다.
7. **명시적 재시도.** 429, 5xx, 네트워크 오류, timeout은 지수 백오프와 지터로 재시도하며 `Retry-After`가 있으면 우선 따른다. 설정 오류(예: 400/401/403)는 재시도하지 않는다. 재시도 횟수는 설정 가능하고 상한이 있다. 사용자에게 보여줄 정책은 별도 후속 결정이다.
8. **원본 이미지 접근.** 에이전트가 `open_source(doc, page)`를 호출할 때만 그 PDF 페이지를 렌더링한다. `(pdf_sha256,page,dpi,renderer_version)` 기준으로 디스크 캐시한다. 검색은 썸네일을 붙이지 않는다. 이 호출은 원본 이미지, PDF 텍스트 레이어가 있으면 그 텍스트, 변환 텍스트/검증 상태, 페이지 출처를 제공한다.
9. **산출물 이미지 안전성.** 최종 답변은 `asset:<id>` 참조만 사용한다. ID는 이번 에이전트 실행에서 실제로 연 페이지 이미지여야 한다. 서버가 반환 전 토큰을 허용된 asset 목록에 대조한다. 프론트 렌더러 구현은 범위 밖이다.
10. **명시적 마이그레이션.** 앱 시작 시 테이블/확장을 생성하지 않는다. DB 변경은 버전 관리된 마이그레이션 CLI에서만 적용한다. 테스트 DB 없이 운영/개발 DB 대상으로 회귀 테스트를 실행하지 않는다.
11. **비밀값.** 프록시 URL/key/model은 `.env`에서 읽고 `.env.example`만 커밋한다. 비밀값은 로그·도구 결과·테스트 출력에 남기지 않는다.
12. **TDD.** 각 단계마다 먼저 실패 테스트를 작성하고 실패를 확인한 다음 구현한다. 실모델/임베딩 호출은 명시적 스모크 테스트에서만 하며 일반 테스트는 더블/로컬 서버를 사용한다.

## 5. 에이전트 도구 계약 (초안)

- `search_manual(query, machines?, top_k?)`: 페이지 텍스트와 검증 메타데이터, 문서/페이지 출처, 연관 페이지, 검색 leg별 상태와 rank를 반환한다. 이미지는 반환하지 않는다.
- `lookup_identifier(value, kind?)`: exact 일치 문서/페이지와 `found`를 반환한다.
- `open_source(doc_sha256, pdf_page, dpi?)`: PDF 원본을 온디맨드 렌더링하고, 이미지 `asset_id`, PDF 텍스트 레이어, 변환 텍스트, 변환 텍스트 원천 표시와 검증 상태를 반환한다.
- DB/PDF 장애는 예외 상세·경로를 노출하지 않고 `database_unavailable`, `source_missing`, `page_not_found`, `source_integrity_error`, `source_render_failed` 같은 구조화 상태로 돌려준다.
- 결과의 `status`는 `answered|insufficient_evidence`다. `answered`는 실제 조회·열람한 출처를 하나 이상 인용해야 한다. `insufficient_evidence`는 관련 없는 출처를 강제로 인용할 필요가 없다. 이 상태는 사용자 응대 문구 정책이 아니라 근거 충족 여부를 나타내는 도구 계약이다. 상태/출처 ID 검증이 답변 내용의 사실성까지 증명하는 것은 아니다.
- CommonMark 파서로 인라인/참조형 이미지 목적지를 모두 검증하며 이번 실행에서 연 `asset:<id>`만 허용한다. raw HTML은 지원하지 않는다. 코드 블록/인라인 코드의 이미지 예제나 `src=` 문자열은 실행 가능한 이미지가 아니므로 거부하지 않는다.
- 에이전트 진입점은 백엔드 Python API와 CLI다. HTTP/프론트 계약은 추후 정한다.
- 결과 객체는 `{status, answer_markdown, citations, assets, tool_calls, retrieval_status}` 형태다.
- `backend/scripts/test_isolated.py`는 별도 임시 `_test` DB를 생성해 회귀 테스트 후 삭제한다. 기존 샘플/임베딩을 테스트 준비 과정에서 지우지 않으며, 테스트 출력의 접속 문자열·키·비밀번호를 마스킹한다. 해당 역할에는 DB 생성 권한이 필요하다.

## 6. 데이터 모델 방향

`rag_document`, `rag_source_alias`, `rag_page`, `rag_identifier`, `rag_page_link`, `rag_embedding_config`, `rag_embedding`, `rag_embedding_api_error`, `rag_query_embedding_cache`, `rag_retrieval_run`, `rag_schema_migration`을 둔다. 원본 PDF는 DB blob이 아니라 파일 경로+SHA로 보관한다. 테스트 코퍼스의 PDF/JSONL은 gitignore 대상이다. 기존 데모 테이블은 새 스키마가 안정화되기 전까지 자동 삭제하지 않는다.

## 7. 비기능 요구사항

- 샘플 규모에서 키워드 검색 p95 50ms 이하, exact vector search p95 100ms 목표(로컬 측정과 실제 DB를 함께 보고 조정).
- PDF 페이지는 최초 요청 시 렌더링하고 후속 호출은 캐시 사용.
- 비밀정보/문서 본문을 오류 로그에 넣지 않는다.
- 전체 문서가 약 3배로 늘어도 증분 적재와 임베딩을 재개할 수 있다.

## 9. 로컬 테스트 코퍼스 선택

초기 샘플은 서로 다른 자료 유형과 일부 의도적 중복을 포함한다: 조사 자료 2개, F510B의 서문/안전/회로도, F400의 Troubleshooting/Maintenance/Safety, F400VM(2064) 및 F500PLUS(2093) 부품표, F500 Troubleshooting. 테스트 데이터는 `backend/data/test_corpus/`에 놓고 git에서 제외한다. 원본 zip은 샘플을 뽑은 후 저장소에서 제거한다. 새 문서는 별도 로컬 입력 디렉터리로 ingest할 수 있어야 한다.

## 10. 문서 종류를 두지 않는 이유

문서를 "트러블슈팅/정비/부품 목록" 등으로 나누는 종류(`document_kind`)는 두지 않는다. 처음에는 원본 파일 경로의 글자(`3-2.`, `parts list` 등)로 추정했는데, 이는 현재 11개 파일 이름에 맞춘 규칙이라 문서가 늘면 어긋나고, 알람·도면 번호를 색인할지 여부까지 이 추정값이 결정하고 있었다. 그래서 식별자 규칙은 **텍스트 자체**만 보고 동작하게 했고(알람: 대소문자 구분 `NNNN 대문자 제목` 줄, 도면 번호: `DWG` 열과 영문자가 들어간 `2064-05G-01` 제목줄), 검색 범위 지정은 데이터가 직접 말해 주는 `machines`로만 한다. 문서의 성격은 제목(`TroubleShooting`, `PARTS LIST`)으로 에이전트가 읽을 수 있다. 종류가 정말 필요해지면 추정이 아니라 변환 데이터에 명시된 값을 쓴다.

알려진 한계: `2016 PARTS LIST` 같은 줄은 알람 제목줄(`2023 SPINDLE …`)과 모양이 같아 알람으로 잘못 색인될 수 있다. 잘못된 식별자는 그 페이지의 정확 일치 결과를 하나 더 만들 뿐이고, 에이전트가 원본 페이지로 확인한다.
