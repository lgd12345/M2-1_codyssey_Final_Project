# 고객사·연락처·설비 관리

운영진(`admin`, 기존 `user`)이 매뉴얼 화면의 **고객사 관리**에서 회사코드·이메일·설비를 관리한다. 고객(`customer`)은 관리 API와 화면에 접근할 수 없다. 기존 회사/연락처(`claim_access.company/contact`)를 재사용하므로 고객 가입·비회원 인증 명부와 별도의 중복 회사 명부를 만들지 않는다.

## 데이터와 화면

- 회사명·고정 회사코드·활성 상태, 실제 연락처의 추가/비활성, 설비 기종명·호기·제조처·확인/활성 상태를 관리한다. 이메일은 수정 대신 새 연락처 추가 후 기존 연락처 중지로 처리한다. 기존 계정의 소속·아이디·권한은 자동으로 이전하거나 변경하지 않는다.
- 한 설비는 UUID 한 행이다. 호기가 있으면 한 대씩, 없으면 1~100대 일괄 등록한다. 등록 대수와 확인된 보유 대수를 구분한다. 비활성 설비는 확인된 보유 대수에서 제외하되 이력과 등록 총수에는 남는다.
- 회사 목록/설비는 페이지당 20개다. 쓰기에는 동일 Origin과 기존 세션/CSRF를 요구한다. 본문은 32 KiB로 제한한다. 클라이언트가 보낸 역할/행위자는 받지 않는다.
- 회사별 쓰기 잠금, 버전 비교로 오래된 편집을 거절한다. 설비 일괄 등록의 요청 UUID와 내용 해시는 같은 요청의 재시도를 중복 저장하지 않는다. 회사코드·회사 내 이메일·회사/기종/호기 중복은 DB 제약으로도 막는다. 삭제 API는 없으며 변경 행위자/시각/필드를 별도 감사 테이블에 남긴다. 감사 JSON에 이메일 원문은 기록하지 않는다.
- 회사/연락처 비활성은 신규 가입·비회원 인증을 막는다. 이미 발급된 계정의 로그인 중지·세션 철회는 기존 계정 관리 절차의 대상이다. 이메일 명부를 수정했다고 계정이 자동 삭제되지는 않는다.
- 이메일별 `미가입/가입`은 기존 `claim_access.registration.contact_id`의 가입 완료 기록을 읽어 표시한다. 중복 상태 컬럼이나 새 migration은 추가하지 않는다. 가입 전 인증번호 요청/인증만으로 `가입`이 되지 않는다. 이메일 사용 중지나 계정 비활성은 가입 완료 이력을 지우지 않는다. 다른 회사의 같은 이메일이나 전역 아이디만으로 회사 소속 가입을 추정하지 않는다. 목록과 상세의 가입 이메일은 가입 완료 기록이 있는 주소만 집계한다. 주소 사용 중지는 가입 이력을 삭제하지 않으므로 가입 이메일 수를 줄이지 않는다. 가입 전 주소는 상세의 등록 이메일에서 미가입으로 관리한다. 실제 가입은 가입 처리 트랜잭션에서 계정과 기존 가입 기록을 함께 저장하므로 운영진은 상태를 수동 변경하지 않는다.
- 설비의 `설비 확인`은 가입 여부와 별개다. 보유 회사·기종·호기의 확인 여부이며 FSR에서 가져온 미확정 자료를 구분한다.

## FSR에서 비공개 참고 명부 생성

`backend` 디렉터리에서 실행한다. 원본 파일은 덮어쓰지 않는다.

```powershell
python -m app.company_admin.prepare '원본.csv' --output '비공개_출력_디렉터리'
```

`설치고객사명`에서 재생성 가능한 회사코드를 만들고 `회사/기종/호기`로 반복 FSR을 묶는다. 회사명 표기의 차이를 임의로 합치지 않는다. `제조처`의 의미를 제조사로 바꾸지 않는다. 같은 기종/호기가 여러 회사에 있거나 제조처가 충돌하면 소속 확인 표시를 남긴다. 모든 원자료 설비는 미확인이다. FSR 수를 구매수량으로 해석하지 않는다.

출력은 `registry-seed.json`, `회사_마스터.csv`, `고객사_설비_관리.csv`, `생성정보.json`이다. CSV 수식처럼 해석될 값은 문자로 이스케이프한다. 원문 기준 값과 내부 UUID는 JSON에 보전한다. 생성 이메일은 예약 도메인 `example.invalid`이며 **비활성·시연 전용**이다. 실제 이메일은 운영진이 회사 연락처임을 확인해 별도로 등록한다. 임시 이메일을 실제 고객의 이메일로 추정하지 않는다.

원본/출력/DB 덤프를 Git·Docker 이미지·웹 정적 디렉터리에 넣지 않는다. 로컬 `backend/private-data/`는 Git 제외 대상이지만 Docker의 앱 복사 경로 밖이며, 실제 관리 파일은 서버의 제한된 경로에 두어야 한다. 시연 데이터와 테스트 어댑터는 운영 앱에 자동 적재/마운트되지 않는다.

## 명시적인 DB 준비와 활성화

웹 시작·Git 푸시·Docker 재빌드는 DDL이나 명부 적재를 실행하지 않는다. 기존 Dockerfile과 서버의 main pull/rebuild 방식은 유지한다. 기본 `COMPANY_ADMIN_ENABLED=0`에서 운영진은 준비 안내를 본다. 이 기능은 SMTP 키나 공개 가입 활성화를 요구하지 않는다.

1. 서버에서 실제 대상 DB 이름·기존 001 적용 이력/체크섬·기존 테이블/데이터·권한·백업/복구 절차를 확인한다. 관리용 `COMPANY_ADMIN_MIGRATION_DATABASE_URL`을 서버의 비밀 설정으로만 제공한다. 접속 문자열/키를 명령줄·로그·Git에 넣지 않는다.
2. 우선 `python -m app.company_admin.manage --expect-database 실제_DB명`으로 읽기 전용 확인한다. 기본 실행은 변경하지 않으며 스키마/권한의 모든 조건을 증명하는 검사는 아니다.
3. 적용 범위가 확정되면 `python -m app.company_admin.manage --apply --expect-database 실제_DB명`을 명시적으로 실행한다. 신규 DB에는 원본 **001 + 새 004**만 적용하며 002/003 역할/이메일 migration은 자동 적용하지 않는다. 적용 이력은 기존 명부 명령과 같은 advisory lock과 트랜잭션에서 관리한다. 기존 체크섬 불일치 시 중단한다. 004를 수정해 재적용하지 말고 후속 migration으로 변경한다.
4. 참고 명부 적재를 별도로 결정했다면 위 명령에 `--seed-file 비공개/registry-seed.json`을 지정한다. 대상 이름과 `--apply` 없이는 적재하지 않는다. 전체를 한 트랜잭션으로 처리한다. 같은 회사코드의 회사명/기존 원자료 설비가 충돌하면 덮어쓰지 않고 중단한다. 재실행은 동일 source key를 중복 생성하지 않는다. 임시 연락처는 SQL에서도 비활성·placeholder로 강제하고 DB CHECK로 활성화를 막는다. 설비는 미확인으로 강제한다.
5. 런타임 계정에는 필요한 SELECT/INSERT/UPDATE와 감사 INSERT/identity sequence 사용 권한만 부여하고 DDL·삭제 권한은 부여하지 않는다. 실제 권한은 서버에서 검증한다. 테이블의 소유자·관리 계정과 런타임 계정을 구분한다.
6. 실제 DB에서 소량 확인 후 `APP_COOKIE_SECURE=1`, `COMPANY_ADMIN_ENABLED=1`을 설정하고 기존 배포 방식으로 재시작한다. 런타임은 기존 `DATABASE_URL`의 001/004 체크섬을 읽기 전용 확인한다. 불일치/연결 실패 시 닫힌다. 운영진/고객 각각 접근·변경·감사·중복/동시 편집을 검증한다. 문제 시 기능 플래그를 0으로 되돌린다. 데이터를 임의 삭제하는 다운 migration은 제공하지 않는다.

로컬 모의 테스트는 실제 PostgreSQL 제약/권한/트랜잭션 검증을 대체하지 않는다. 운영 DB 적용과 실제 명부의 확정은 코드 배포와 별도 작업이다. 공개 고객 가입 활성화에는 기존 002/003·정책·SMTP 준비 요건이 그대로 적용된다.

## 로컬 검증

```powershell
python -m pytest --noconftest tests/test_company_registry.py -q
```

API 테스트는 실제 DB 연결을 금지하고 메모리 저장소로 권한·CSRF·입력·버전/중복·소속 범위를 검증한다. SQL 경계·명부 변환/검증·명시 적용 조건도 검사한다. 실제 PostgreSQL 검증은 별도 서버 준비 단계에서 수행한다.

운영진의 공통 메뉴는 매뉴얼·고객사 관리·로그아웃이다. 로그인한 운영진의 공개 홈/로그인/가입/비회원 주소는 업무 화면으로 정리한다. 로그인한 고객은 고객지원·고객센터를 이용하며 가입/로그인 화면을 반복해서 표시하지 않는다. 익명 공개 홈은 세션 확인 실패와 무관하게 표시하고, 보호 화면은 인증 확인 실패 시 재시도를 제공한다.
