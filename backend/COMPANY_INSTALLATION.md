# 고정 001·004 설치 작업

기존 main → 서버 pull → Docker 재빌드를 유지하면서 기존 내부 DB 연결에 **새 claim_access 구조만** 명시적으로 설치한다. 앱 시작에서는 실행하지 않는다. 회사/계정/이메일 자료를 적재하거나 기존 인증 테이블·권한·메일·기능 플래그를 변경하지 않는다.

`/api/v1/companies/installation`은 운영진 로그인과 배포 승인 파일이 모두 있어야 열린다. 배포 승인 파일 `app/company_admin/installation-grant.json`은 지정 계정의 UUID 해시, 무작위 일회 승인 코드의 SHA-256, HTTPS 출처, 1시간 이내 유효기간, 001/004 SQL 체크섬과 작업 ID를 지정한다. 파일이 없거나 만료·불일치하면 모든 작업은 닫힌다. 원문 승인 코드는 Git 제외 private-data에만 보관하고 저장소/URL/로그에 넣지 않는다. 승인은 배포 권한자가 검토한 소스 변경으로만 제공한다.

설치 화면의 상태 확인은 읽기 전용이다. 대상 확인값은 DB 이름/관측 서버/역할 등의 비밀값 없는 식별 정보로 계산한 해시이며 DSN이나 비밀번호 해시가 아니다. 전역 클러스터 신원을 증명하는 값은 아니다. POST는 계정·승인 코드·출처·CSRF·대상 확인값·확인 체크를 모두 검사한다. 임의 SQL/명령/DSN/파일 경로 입력은 받지 않는다.

대상에 기존 claim_access가 있으면 일치한 이번 작업 영수증이 있는 경우의 재조회 외에는 중단한다. DB 잠금 아래 엄격한 CREATE SCHEMA로 생성 경쟁도 차단한다. 기존 CLI와 같은 고정 SQL·체크섬·트랜잭션 잠금을 사용하며 001/004 전체와 설치 영수증을 한 트랜잭션으로 처리한다. SQL/검증 실패 시 새 구조는 롤백한다. 기존 인증·RAG 구조와 자료는 변경하지 않는다. 성공 후 반복 요청은 이력 확인만 하고 새 변경을 하지 않는다. 영수증은 새 스키마의 COMMENT에 작업 ID·주체/대상 해시·시각으로 남으며 원문 승인 코드는 포함하지 않는다.

실제 적용 전 기존 서비스/대상과 권한을 확인하고, 테스트·실제 브라우저 검증 뒤 승인 파일을 배포한다. 원본 DB에 이미 존재하던 자료를 덮어쓰는 작업은 이 경로로 실행할 수 없다. 적용 뒤 기존 읽기 진단에서 001/004 일치와 필수 테이블을 확인하고 **승인 파일을 즉시 제거해 main에 반영**한다. 승인 코드도 로컬에서 폐기한다. 새 고객 가입용 002/003, 고객사 자료 등록, 보안 쿠키/기능 플래그, SMTP/정책 설정은 별도 작업이며 이 설치의 성공을 전체 활성화로 표시하지 않는다.

```text
python -m pytest --noconftest tests/test_company_installation.py -q
```

실제 엔진 검증은 [격리 PostgreSQL 지침](./POSTGRES_CUSTOMER_ACCESS_TESTS.md)에 따라 `tests/test_company_installation_postgres.py`도 실행한다. 기존 운영 DB를 테스트 대상으로 사용하지 않는다. 설치 전/후 기존 사용자 해시·역할/세션 유지, 대상 변경/기존 미확인 구조 거절, 동시 요청 1회 생성, 실패 후 전체 롤백을 실제 엔진에서 확인한다. 이 시험이 운영 전체 DB의 백업/복원 검증을 대신하지 않는다.
