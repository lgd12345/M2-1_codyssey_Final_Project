# 고객 계정·비회원 문의 운영 안내

이 기능은 코드와 화면 검증 단계입니다. 기본값은 비활성이며, 웹 시작·Docker 재빌드·main 배포는 migration이나 회사 등록을 실행하지 않습니다. 기존 인증 쿠키·세션과 main 갱신 → 서버 pull → Docker 재빌드 방식을 유지합니다.

## 계정과 권한

| 구분 | 발급 | 허용 범위 |
|---|---|---|
| 고객 `customer` | 사전 등록된 회사 연락처의 이메일 인증 후 비밀번호 설정. 인증 이메일이 로그인 아이디 | 서버가 확인한 본인 회사의 고객 화면 |
| 운영진 `user` | 신뢰된 관리 환경에서 수동 발급 | 기존 내부 매뉴얼·문서·AI 기능 |
| 시스템 관리자 `admin` | 신뢰된 관리 환경에서 제한적으로 수동 발급 | 운영진 기능 및 기존 관리자 진단 |
| 비회원 | 회사 연락처 이메일 인증 | 30분 세션에 연결된 문의 한 건 작성·조회 |

기존 `admin`·`user` 계정은 변경하지 않습니다. 공개 가입은 역할·회사 ID를 받지 않으며 `customer`만 만듭니다. 고객/비회원은 서버에서도 매뉴얼·실행 기록·문서·첨부 자산·AI API에 접근할 수 없습니다. 회원 전용 정식 클레임 접수·이력 관리와 운영진의 문의 처리 화면은 후속 단계입니다. 현재 비회원 문의 저장은 에이전트 실행·배정·알림메일을 유발하지 않습니다.

## 운영 활성화 전 필요한 확인

1. 실제 서버에서 인증 DB와 업무 DB의 대상·권한·PostgreSQL 버전·기존 제약·관리 실행 경로·백업/복구 방법을 확인합니다. 로컬 모의 테스트는 PostgreSQL migration 실검증을 대체하지 않습니다.
2. 선택한 비운영 DB에서 아래 migration을 단일 실행하고 기존 로그인/운영진 접근·가입·중복/동시 요청·구버전 코드 호환성을 검증합니다. 실제 운영 적용은 별도 승인 범위입니다.
3. 실제 회사코드·회사명·허용된 연락처를 관리자가 확인해 등록합니다. 회사코드만 알아서는 가입/문의가 허용되지 않습니다. 공용 메일함은 계정 공유 위험이 있으므로 개인별 업무 연락처를 사용합니다.
4. 개인정보 목적·항목·보유기간·처리/전달 대상·문의/철회/삭제 경로를 확정합니다. 보유기간에 맞는 삭제·철회 운영 절차와 실행 책임, 백업/메일 사업자의 잔존 데이터 처리도 확인합니다. 코드에는 임의의 법적 안내값을 넣지 않았습니다. 만료 인증번호만 제한적으로 정리하며 문의/계정의 보유기간 삭제는 자동 구현되어 있지 않습니다.
5. Resend의 검증된 발신 도메인과 전용 SMTP 자격 증명을 준비하고 서버에서 TLS·소량 발송·실제 수신함 도착을 검증합니다. 메일 공급자 장애 중에는 코드를 사용 가능 상태로 만들지 않습니다. 자동 재발송하지 않습니다.
6. 기존 HTTPS/프록시가 실제 클라이언트 주소를 신뢰된 경로로 전달하는지 확인합니다. 애플리케이션은 `request.client.host`만 사용하며 임의의 `X-Forwarded-For`를 직접 신뢰하지 않습니다. 프록시 주소만 보이면 요청 제한이 모든 사용자에게 합산될 수 있습니다. 확인 없이 프록시 신뢰 범위를 넓히지 않습니다.
7. 런타임 DB 계정은 필요한 테이블/열의 최소 조회·삽입·갱신 권한과 만료 인증번호 정리 권한만 부여하고 DDL 권한은 별도 관리 계정에 둡니다. 장애/발송량 관측과 비활성화·코드 복귀 절차를 시험한 뒤 플래그를 켭니다.

## DB 적용을 자동 실행하지 않는 관리 명령

아래 명령은 `backend` 또는 컨테이너 `/app`에서 실행합니다. 비밀번호/DSN/회사 연락처 원문을 커밋·채팅·명령 인수에 넣지 않습니다. 관리 환경에서 `CUSTOMER_ACCESS_MIGRATION_DATABASE_URL`을 명시적으로 선택합니다. 다른 DB 환경변수로 대체하지 않습니다.

```text
python -m app.customer_access.manage
```

기본 명령은 읽기 전용으로 버전 테이블 존재 여부만 확인합니다. 쓰기는 `--apply --expect-database 실제DB명`이 모두 필요하고, 실제 DB명이 다르면 중단합니다.

```text
python -m app.customer_access.manage --apply --expect-database 실제DB명
python -m app.customer_access.manage --apply --expect-database 실제DB명 --with-customer-role
python -m app.customer_access.manage --apply --expect-database 실제DB명 --with-customer-email
python -m app.customer_access.manage --apply --expect-database 실제DB명 --company-file 관리환경의_비공개_JSON_경로
```

첫 명령은 별도 `claim_access` 스키마와 migration 이력을 트랜잭션/관리 잠금 안에서 만듭니다. 둘째 명령은 **선택한 인증 DB**의 `public.app_user` 역할 제약만 `admin/user/customer`로 확장합니다. 기존 제약 이름·정의가 예상과 다르면 중단하며 자동 우회하지 않습니다. 기존 계정·비밀번호·기존 migration은 수정하지 않습니다. 적용 이력의 체크섬이 다르면 중단합니다. LF/CRLF 차이는 체크섬에 영향을 주지 않습니다.

`--with-customer-email`은 검증된 역할 migration `002` 이후에만 별도 `003_customer_email.sql`을 적용합니다. 기존 로그인 ID 제약의 정확한 정의를 확인한 뒤, 기존 ID를 모두 허용하면서 고객 역할에만 최대 254자의 이메일 문자 범위를 추가합니다. 기존 계정/소속을 변경하거나 과거 고객 ID를 이메일로 자동 전환하지 않습니다. 실제 적용 전 PostgreSQL에서 제약 정의와 기존/신규 코드 호환성을 검증해야 합니다. 가입 기능의 준비 확인은 `003` 이력까지 요구하므로 이전 DB에서 새 이메일 가입이 잘못 활성화되지 않습니다.

회사 입력 JSON은 `code`, `name`, `emails`(문자열 배열)가 필요합니다. 실제 운영 파일은 버전 관리 밖에서 접근 권한을 제한합니다. 기존 회사명 충돌·비활성 회사는 덮어쓰거나 재활성화하지 않습니다. 연락처 철회·회사 정지와 보유기간 삭제는 운영 절차에서 담당합니다.

운영진은 공개 가입 대신 별도 명령으로 발급합니다. 비밀번호는 비공개 프롬프트로 입력합니다. 기본 `user`는 일반 운영진이며 `admin`은 시스템 관리가 필요한 사람에게만 명시적으로 선택합니다.

```text
python -m app.customer_access.manage --apply --expect-database 실제인증DB명 --create-operator 운영진아이디
```

## 설정과 실패 시 동작

`customer-access.env.example`은 모든 플래그가 `0`이고 자격 증명이 비어 있습니다. 실제 개인정보 안내 JSON 파일에는 비어 있지 않은 문자열 `version`, `purpose`, `items`, `retention`, `recipients`, `contact`, `refusal`가 필요합니다. 운영 파일을 커밋하지 않습니다.

`CUSTOMER_ACCESS_ENABLED=1`, `CUSTOMER_ACCESS_RELEASE_APPROVED=1`, `APP_COOKIE_SECURE=1`, 명시적 `DATABASE_URL`, 32자 이상 무작위 전용 `CUSTOMER_ACCESS_SECRET`, `CUSTOMER_MAIL_FROM`, `CUSTOMER_SMTP_PASSWORD`, `CUSTOMER_ACCESS_POLICY_FILE`과 일치하는 migration 이력이 모두 있어야 서비스가 열립니다. 안내 버전은 120자 이내로 관리합니다.

가입은 추가로 `CUSTOMER_REGISTRATION_ENABLED=1`과 **인증 DSN(`RAG_DATABASE_URL` 우선) 및 `DATABASE_URL`의 정확한 문자열 일치**, 역할·이메일 migration 이력이 필요합니다. 현재 구현은 한 DB 트랜잭션으로 계정·회사 소속을 함께 저장합니다. 실제 두 DB가 분리되어 있으면 공개 가입은 닫힙니다. 임의로 인증 DB를 바꾸거나 두 DB에 부분 저장하지 말고 별도 설계를 검토합니다. 비회원 문의만은 별도 업무 DB로 운영할 수 있습니다.

`GET /api/v1/access/status`에서 상태를 확인합니다. 비활성일 때 `{available:false, registration_available:false, policy:null}`이며 개인정보 입력 폼을 노출하지 않습니다. 활성 후에는 스키마 버전 일치 여부를 읽기 전용으로 확인합니다. 원래 health 경로의 200 응답만으로 인증 기능 준비 완료를 판단하지 않습니다.

긴급 중지는 `CUSTOMER_ACCESS_ENABLED=0` 후 기존 배포/재시작 절차로 수행합니다. 새 가입·비회원 API는 닫히며 기존 운영진 로그인/매뉴얼 기능을 유지합니다. 고객 프로필도 닫힙니다. 계정/문의/발송 기록이나 적용된 스키마를 임의 삭제하지 않습니다. 코드 복귀와 DB 복구는 구분합니다.

## 보안과 현재 검증 범위

인증번호는 6자리·10분·최대 5회·일회성이고, 브라우저의 무작위 증명·목적·연락처·안내 버전에 결합된 HMAC만 저장합니다. 연락처/클라이언트 제한 키도 HMAC입니다. 클라이언트와 이메일별 10분 5회, 이메일 재요청 60초 제한을 DB 잠금으로 직렬화합니다. 등록되지 않았거나 비활성인 회사코드는 명시적인 오류로 안내하고 발송하지 않습니다. 해당 시도도 클라이언트 제한에 기록하되 회사코드를 바로 수정할 수 있도록 정상 이메일의 재발송 대기와 구분합니다. 사용자 지시에 따라 회사 명부와 일치하지 않는 이메일도 명시적인 입력 오류로 안내하고 발송하지 않습니다. 이 선택은 회사코드/연락처의 일치 여부가 응답으로 구분되는 대신 입력을 바로 고칠 수 있게 합니다. 실제 등록된 이메일 주소·회사명·고객 계정 정보는 오류에 반환하지 않고 거절된 요청에도 동일한 요청 제한을 적용합니다.

가입은 회사/이메일 확인 → 이메일 인증 → 비밀번호 설정 순서입니다. 공개 가입 API는 아이디·이메일·역할 입력을 받지 않고, 인증된 연락처에서 서버가 정규화한 이메일을 가져와 `customer` 계정을 만듭니다. 별도 아이디 입력·중복 확인 버튼이나 공개 아이디 조회 API는 없습니다.

`/api/v1/access/registration/verify`는 올바른 이메일 인증번호를 확인한 뒤 기존 연락처 가입 또는 전역 이메일 아이디 중복을 확인합니다. 이미 사용 중이면 `already_registered`만 반환하고 코드를 소비하며 화면에 기존 계정 로그인 링크를 표시합니다. 비밀번호 재설정이나 자동 로그인은 수행하지 않습니다. 기존 계정/역할/회사 소속을 덮어쓰지 않습니다. 회사코드는 여러 직원이 공유할 수 있지만 이메일 로그인 아이디는 기존 인증 테이블의 전역 unique 제약을 따릅니다. 같은 이메일을 다른 회사코드로 인증해도 기존 계정의 소속을 자동 이동하거나 운영진 권한을 부여하지 않습니다. 기존 회원도 비회원 문의는 별도로 이용할 수 있습니다.

이메일 인증 후 신규 가입 단계에서는 인증된 로그인 이메일을 읽기 전용으로 표시합니다. 최종 가입 시에도 코드·연락처 활성 상태를 재검사하고 DB unique 제약으로 중복 생성을 차단합니다. 확인 뒤 다른 요청이 먼저 가입했으면 기존 계정 로그인 안내로 돌아갑니다. 이메일은 `+` 주소와 긴 주소·IDN 도메인 정규화를 지원합니다. 고객 생성만 이메일로 제한하고 기존 운영진의 3~64자 ID 규칙과 기존 세션은 유지합니다. 긴 이메일의 로그인 실패 키는 64자 이하 해시로 저장하여 기존 실패 테이블 제약을 유지하며 서로 다른 이메일을 임의로 잘라 같은 키로 취급하지 않습니다.

비회원 쿠키는 별도 경로의 Secure/HttpOnly/SameSite=Strict 쿠키이며 원본 인증 쿠키와 분리합니다. 쓰기에는 Origin 검사와 CSRF 검사가 적용되고 입력 길이·요청 본문 크기를 제한합니다. SQL은 값을 바인딩하고 비밀번호/인증번호/SMTP 오류 원문을 HTTP 오류에 반사하지 않습니다. 문의는 세션으로만 조회하며 외부 회사 ID·문의 ID를 신뢰하지 않습니다. 같은 문의의 재전송은 기존 결과를 반환하고 다른 내용으로 덮어쓰지 않습니다.

로컬 단위/API 테스트와 실제 브라우저 시험은 합성 회사·계정·메모리 저장소·가짜 메일만 사용합니다. 실제 PostgreSQL DDL/권한·운영 계정 로그인·실메일 수신·서버 재시작 복구·삭제 운영의 검증은 별도로 남아 있습니다. 시험 통과를 근거로 운영 활성화를 선언하지 않습니다.

## 동의 거부 고지 준비

`refusal`에는 동의 거부권과 거부 시 제한되는 기능을 실제 운영 정책에 맞게 작성한다. 이 항목도 없거나 빈 값이면 활성화 설정이 있어도 고객 인증은 닫힌다. 기존 6개 항목의 정책 파일은 자동 보완하지 않는다. `customer-access.policy.example.json`은 전 항목이 빈 안전한 양식이며 그대로는 활성화할 수 없다. 실제 정책은 Git 밖에서 관리하고 고지 내용을 변경하면 새 정책 버전과 재동의 범위를 확인한다. 빈 문자열 검사는 문구의 법적/운영적 정확성 검증을 대체하지 않는다. 실제 보유기간·처리업체·철회/삭제 절차는 서비스 책임자가 확정해야 한다.
